# v0.3.0 备份协议与恢复方案

状态：v0.3 开发协议，2026-10-24。实现与实际验收状态见 [v0.3 验证日志](v0.3.0-validation.md)；本文描述约束，不代表全部人工验收通过。取代 [设计稿](design-review.md) 中的早期备份草案。v0.3 的其他质量门槛仍见 [开发规划](roadmap.md)。

## 范围与决定

- 单个 UTF-8 JSON 文件，建议名 `seen-backup-YYYY-MM-DD-HHmmss.json`，MIME `application/json`。海报以 Base64 内嵌，文件可离线跨设备、跨 debug/release 包恢复。
- 导出全部 Movie（包括没有观看记录的电影）、全部 Viewing 和被它们引用的本地海报。不联网补图，不改 ID、时间、文本或 null。
- 仅支持覆盖恢复，不合并、不按片名或 TMDB ID 自动去重。导入文件本身的重复 ID/TMDB ID 必须拒绝。
- 不导出 TMDB 凭据、草稿、偏好、外部 URI、机器路径、数据库文件或签名。目标设备凭据与偏好保留。主题尚无可选实现，不纳入协议。
- 有未保存草稿时，允许导出已保存数据；禁止开始恢复，提示先保存或明确放弃草稿。恢复不替用户丢弃输入。
- 备份明文包含观影记录和感受，在导出入口说明；首版不实现加密、压缩、云同步或分卷。
- `schemaVersion` 是备份协议版本，独立于 Room version。首版为 1；当前 Room v1 不因备份功能改表。

## 文件结构

以下为可解析的无海报示例；示例内容为合成数据。

```json
{
  "format": "seen-backup",
  "schemaVersion": 1,
  "appVersion": "0.3.0",
  "exportedAt": "2026-10-24T06:00:00Z",
  "movies": [{
    "id": "3d111111-1111-4111-8111-111111111111",
    "title": "示例电影",
    "originalTitle": null,
    "releaseYear": 2023,
    "releaseDate": null,
    "tmdbId": null,
    "posterAssetId": null,
    "source": "MANUAL",
    "directorNames": null,
    "runtimeMinutes": null,
    "productionCountries": null,
    "createdAt": "2026-10-23T05:00:00Z",
    "updatedAt": "2026-10-23T05:00:00Z"
  }],
  "viewings": [{
    "id": "7a222222-2222-4222-8222-222222222222",
    "movieId": "3d111111-1111-4111-8111-111111111111",
    "viewedDate": "2026-10-22",
    "viewedTime": null,
    "location": "家里",
    "ratingHalfStars": null,
    "notes": "合成验收记录 🎬",
    "createdAt": "2026-10-23T05:00:00Z",
    "updatedAt": "2026-10-23T05:00:00Z"
  }],
  "assets": []
}
```

Movie 与 Room 字段一一对应，唯一改名为 `posterKey` → `posterAssetId`，避免暴露应用内文件名。`directorNames`、`productionCountries` 保持现有实体的可空字符串，**不是数组**；首版不拆分现有字符串，否则往返会改变原数据。没有持久化的 `posterRemotePath` 不进入协议。

有海报时，`assets` 每项包含以下全部字段：

| 字段 | 类型与含义 |
| --- | --- |
| `id` | 规范小写 UUID；Movie.posterAssetId 引用此 ID |
| `mimeType` | 固定 `image/jpeg`，对应现有 PosterStore 输出 |
| `sha256` | 64 位小写十六进制，对 Base64 解码后的原始 JPEG 字节计算 |
| `base64` | 标准 Base64，含规范补位、不含换行；不是 data URI |

同一个本地海报 key 在单次导出中对应同一个 asset ID；多个电影可以共享它。不要求跨次导出的 asset ID 相同。恢复保留电影/观看 ID 与海报原始字节，内部海报文件 key 可以变化，不重新压缩图片。

## 类型、完整性与兼容规则

- 示例中的所有字段均必须出现；可空字段须用 JSON `null`，不能用缺字段、空字符串、0 或午夜代替。原本合法的空字符串原样保留，不在恢复时 trim。顶层必须是对象；数组不能为 null。
- 严格检查 JSON 类型：数字字符串不能冒充整数，浮点数/溢出数字不能截断为整数；字符串不能由 JSON 库隐式转换而来。拒绝重复对象字段、尾随内容、非法 UTF-8、未配对代理字符和超深嵌套。未知字段允许有界跳过；不据此接受未知版本。
- `format` 必须匹配；仅接受 `schemaVersion: 1`。高版本拒绝并提示更新应用；没有版本的旧草案不是受支持的备份。将来支持旧协议时，先转换成当前 DTO，再执行同一套预检。
- Movie.id、Viewing.id、Viewing.movieId、asset.id 均为规范小写 UUID。各实体内 ID 唯一；非空 TMDB ID 为正 Long 且在电影间唯一。所有观看必须引用文件内电影；所有非空海报引用必须存在；未被任何电影引用的 asset 拒绝。允许空库和零观看电影。
- `title` 非空白、最多 300 Unicode 码点；`originalTitle` 最多 300；`location` 最多 200；`notes` 最多 50,000。导演/国家字符串各最多 10,000 码点。上限按码点而非 UTF-16 长度计数，不裁剪文本。
- `releaseYear` 为 null 或 1800–9999 整数；`releaseDate` 为 null 或有效 ISO LocalDate，不强制与年份相等。`runtimeMinutes` 为 null 或非负 Int（兼容 TMDB 返回 0）；`source` 仅 `MANUAL` / `TMDB`。不额外要求 source 与 tmdbId 同时存在，避免引入旧数据没有的约束。
- `viewedDate` 为有效 ISO LocalDate；`viewedTime` 为 null 或有效 ISO LocalTime。历史未来日期只警告可能存在设备时钟差异，不以当前日期拒绝恢复。`ratingHalfStars` 为 null 或 1–10 整数，null 与最低分不同。
- `createdAt`、`updatedAt`、`exportedAt` 必须能解析为 UTC Instant，恢复原字符串；不以当前时钟或创建/更新时间先后拒绝历史数据。`appVersion` 为最多 64 码点的非空字符串，只作来源说明，不参与协议兼容判断。
- 海报必须通过 Base64、SHA-256、JPEG 内容识别、尺寸及实际解码检查。扩展名/MIME 声明不能代替内容验证。先检查大小和图像边界，再分配位图；不把外部 asset ID 拼接成路径。

## 资源上限

导出与导入使用同一组限制；超限报错，不悄悄丢电影、观看或海报。

| 项目 | 上限 |
| --- | --- |
| 整份 UTF-8 JSON | 100 MiB（104,857,600 字节），含 Base64 |
| Movie / Viewing | 10,000 / 100,000 项 |
| asset | 10,000 项；解码后 JPEG 总量 60 MiB |
| 单张 JPEG 原始字节 | 2 MiB；Base64 长度先按该值约束 |
| 海报尺寸 | 两边均为正，最长边 2,048px |
| JSON 嵌套深度 | 16 层，包括被跳过的未知字段 |

使用有界流式读写，不对 100 MiB 文件调用 `readText()` 或构建包含全部 Base64 的 JSONObject 树；海报逐张暂存、验证和释放。数量上限不保证这么多长感受都能装入文件，总字节限制始终优先。导出快照也应限制数量和累计文本大小。

现有本地图片导入只限制输入和尺寸，未保证压缩输出 ≤2 MiB，因此导出必须实际检查。超限提示具体海报问题，不自动转码；后续可增加单独的媒体压缩能力。

## 导出流程

1. Repository 在 Room 读取事务内取得一致的 Movie/Viewing 快照；与恢复、保存及海报删除共享应用级写入协调。快照读取海报期间防止被并发清理，不能只从 UI 当前筛选结果导出。
2. 在私有暂存文件中流式生成 JSON；只读取快照引用的私有海报。引用存在但文件缺失/损坏时终止并说明原因，避免生成声称完整却丢海报的备份。真正无海报的电影正常导出 null。
3. 关闭文件后，通过与导入相同的预检器验证暂存文件；通过后再启动系统创建文档流程。取消选择只清暂存，不改库。
4. 将已验证的暂存文件复制到所选文档；写入、flush、close 均成功才提示“已导出”。本地失败不打开文件选择器；远端提供器失败尽力删除本次新建文档，提示可能留下不完整文件。
5. 不声称 SAF 提供器具有原子替换能力，也不声称 close 成功代表云端已经同步。导出不能覆盖或删除用户此前选择之外的其他文件。

## 导入预检与确认

1. 从系统打开文档流程取得 URI，在读取中限制总字节，复制到私有、随机命名的操作目录。外部文件此后再被修改不影响本次恢复。不持久依赖 URI 权限。
2. 完整预检并将海报写入操作暂存区；此阶段禁止修改正式数据库和已有海报。记录私有备份文件摘要，预览与最终提交使用同一份内容。
3. 展示来源版本/导出时间、文件内总电影/观看/海报数及当前库总电影/观看数；电影数包含零观看项，说明与主页数量可能不同。显示未来日期等警告。
4. 明确写出“将替换本机全部电影与观看记录，不能合并”，提供“先导出现有数据”“取消”“覆盖恢复”。空库备份同样确认，不把空数组当损坏。恢复前导出失败或取消时留在预览，不自动继续覆盖。
5. 预览期间通过协调器阻止本应用其他库写入及新编辑，已有草稿则禁止进入；读取/浏览仍可用。旋转由 ViewModel 保留本次预览，进程重建则丢弃未确认预览并重新选文件，不能自动覆盖。
6. 确认后检查私有文件摘要/暂存媒体仍一致并再次检查草稿与写入锁；文件损坏、空间不足或状态失效时终止。明确取消时释放锁并清暂存。

## 覆盖恢复与回滚

核心约束：**数据库提交之前不删除、不覆盖任何旧媒体；数据库只引用已经写好并关闭的新文件。** SQLite 事务是唯一的数据提交点，不重命名/替换正在打开的 Room 数据库，不复制 WAL 文件。

1. 确认后继续持有写入协调锁，为每张导入海报分配新的随机 UUID 文件 key，独占创建；若碰撞则重新分配。将已验证字节写入正式海报目录，flush、文件描述符 sync 并关闭，再复查长度/哈希。不能复用或覆盖旧 key，即使 asset ID 或哈希相同。
2. 所有新媒体就绪后，执行单个 Room 事务：先删 Viewing，再删 Movie，插入全部 Movie（海报引用映射到新 key），最后插入全部 Viewing。任何语句失败均抛出异常回滚；不能在事务内部吞掉错误后继续。
3. 事务返回成功即恢复成功。刷新库并退出预览；后续清理失败只提示“恢复已完成，临时文件稍后清理”，不能提示“恢复失败，原库未变”。不再写凭据、偏好或清草稿，不引入额外提交点。
4. 事务失败时原库仍在；清理本操作新建且确认未被当前库引用的文件。清理失败保留文件待后续处理，不能为清理抹去原始失败原因。不能在异常分支不查引用就删除全部新文件。
5. 旧媒体延后清理，首版不必立即回收。清理必须持相同协调锁，排除当前电影引用、草稿引用和进行中的操作；启动时先恢复/读取草稿与数据库，读取失败则不做媒体清理。只处理应用拥有的已知文件名，不跟随外部路径。

| 失败或中断位置 | 数据与媒体结果 | 用户可见行为 |
| --- | --- | --- |
| 选文件取消、读取/预检失败 | 原库、旧海报、草稿完全保留 | 取消或说明格式/引用/超限原因 |
| 新海报写入失败、磁盘不足 | 数据事务尚未开始，旧库不变；可能留未引用新文件 | 恢复失败，可重试 |
| 删除/插入 SQL 失败、事务取消 | Room 回滚原电影/观看；旧媒体完整 | 恢复失败，可重试 |
| 写新媒体后、事务提交前进程退出 | SQLite 恢复旧库；可能有孤立新媒体 | 再启动仍可读旧库，不自动重试覆盖 |
| 提交期间进程退出 | SQLite 恢复为完整旧库或完整新库，两者媒体均保留 | 启动按实际库读取；不猜测事务结果并删媒体 |
| 提交后 UI 更新或清理失败 | 新库已生效，新媒体完整，旧媒体可能暂留 | 重新读取库；不能宣称已回滚 |
| 导出目标写入失败 | 本机库不变，文档提供器可能留半文件 | 明确导出失败，不显示成功 |

协程取消可能发生在事务已提交、调用方收到成功之前，所以必须把“提交结果未知”与“已确认回滚”区分开；取消后重新读库核实，异常处理仅按当前引用清理。进程崩溃恢复验收与断电/存储硬件损坏是不同边界；本方案不承诺跨 SQLite 与文件系统的硬件级分布式事务。

## 实现顺序与验收

保持单模块和手动注入；UI → ViewModel → 备份 Repository/Service → Room、PosterStore。协议 DTO、校验规则、读写器和恢复协调分开，复用平台 JSON 流式 API，不引入新框架。

1. DTO/校验规则与流式读写器：合成夹具、严格类型、Unicode/null、版本、引用、限额、图片校验测试。
2. 导出：一致快照、私有暂存、同预检器自检、系统创建文档、取消/关闭失败反馈。
3. 导入：系统选文件、私有预检、统计预览、明确覆盖确认、草稿/并发写入保护。
4. 恢复：新媒体准备、单事务覆盖、提交结果核实、延迟清理；故障注入覆盖每个边界。
5. API 36 隔离实例执行完整往返和进程退出测试；最后进行版本质量回归及交付验证。

必须覆盖的验收用例：

- 从隔离源库导出到隔离目标库恢复，比较全部字段、ID、时间、零观看电影、重看次数及海报 SHA-256；恢复后断网、重启仍一致。
- 中文、组合字符、emoji 上限与超限；null 评分/时间/文本、午夜、半星、长感受；年份/片长/TMDB 资料原样往返。
- 重复字段/ID/TMDB ID、坏引用、坏 UTF-8/JSON/Base64/哈希/JPEG、负数/浮点/数字字符串/溢出、高版本、截断文件及全部限额，均不改原库。
- 空库导出/覆盖、文件读取中断、提供器拒绝写入或 close 失败、目标取消、旋转/重建、草稿存在及并发写入。
- 媒体写入一半失败、媒体全部准备后失败、SQL 删除后/插入中失败；比较原库所有字段和旧媒体，验证回滚及重试。
- 在媒体准备后、SQL 事务内、提交后分别由外部测试控制进程终止，再启动核对库与全部引用；不能仅以抛异常代替真实进程终止。
- 基于实际旧 APK 创建的隔离合成库覆盖升级，不改历史 Room schema；不得接触用户真实实例。
- 恢复预览/确认/进度/失败反馈在 TalkBack、200% 字号和窄屏下可操作；整个应用的质量回归按 roadmap 单独记结果。

JVM 测试覆盖纯业务规则；API 36 覆盖平台 JSON、Room、媒体、文档提供器和 UI。交付前运行 `bash scripts/check.sh` 和隔离设备检查，保存同一源码/APK 的哈希与报告。失败注入、进程退出、人工无障碍及旧 APK 升级分别记录，不能用编译或配置检查代替。

## 想看片单扩展（v1.1.0，未发布）

电影可附加布尔字段 `wantToWatch`，导出始终写入；旧备份缺少时按 false 读取，非法类型拒绝。协议 `schemaVersion` 仍为 1，扩展沿用未知字段兼容规则。旧版本应用能读取电影与观看，但会忽略想看状态；保留片单请使用支持此字段的版本恢复。零观看电影允许存在，想看状态与观看历史独立。
